Run `python3 Scripts/History/generate_archive.py` from any directory to refresh the bundled archive. Python 3 and ordinary `curl` are required; hosted Ubuntu runners and macOS include curl. The generator fetches all 17 Coin Metrics CSV archives, the fixed pre-March-2024 Frankfurter period with the approved 66 providers, and dated Fawaz USD tables through the latest completed UTC month. March 2024 uses March 2; subsequent months use their first day. The current month is excluded. `--today YYYY-MM-DD` makes the cutoff deterministic; the three `--*-input` options accept saved source snapshots for reproduction.

Run `python3 -m unittest discover -s Scripts/History -p 'test_*.py'` for generator checks. All sources must succeed and validate before an atomic output replacement. Loss of any previously bundled observation date fails for manual review, even if newer observations would keep the row count unchanged. Acquisition dates and input hashes alone never rewrite the archive; selected observations, provider selection, sampling, source links and licence changes do. Full licences and notices remain separate resources beside the JSON. Frankfurter uses the documented ordinary curl client with a 120-second limit, without overridden user agents, spoofed headers, proxies, cookies or authentication. Coin Metrics and Fawaz use Python HTTPS. An upstream HTTP denial or malformed response stops the refresh without falling back to unapproved FX sources.

`Refresh bundled history` runs at 06:00 UTC on the first day of each month and supports manual dispatch on `main`, after this workflow is merged. It reuses an open bot-authored PR under `chore/bundled-history-refresh-*`, skipping commits when its actual head already contains the same semantic content. With no open managed PR, it creates a fresh run-specific branch from current `main`; retained closed or squash-merged branches are ignored. It never pushes to `main`, force-pushes, approves or merges a PR. An unexpected change on the managed branch stops publication for manual review. Upstream failures leave the existing archive and update branch unchanged. If `main` advances during generation, rerun the refresh against the new base.

Pull requests changing `Scripts/History/**` or this workflow run the same full-source generation on GitHub's Ubuntu runner using the PR merge SHA. This dry run has read-only repository permissions, no persisted checkout credentials or private secrets, no candidate artifact upload, and no publishing job. It uses a separate concurrency group from scheduled refreshes. Upstream denials still fail the check and leave publication disabled; a successful dry run validates live generation in the intended runner environment before merging.

Repository Actions settings must permit GitHub Actions to create pull requests (`Allow GitHub Actions to create and approve pull requests`); the workflow uses that setting only for creation. It needs no PAT or other private credential. Only the publishing job receives `contents: write` and `pull-requests: write`.

[GitHub documents](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) that `GITHUB_TOKEN` does not trigger ordinary push workflows; bot-created or updated pull requests can create approval-required workflow runs. A maintainer must choose **Approve workflows to run** when prompted and require the normal Tests checks before merging. This automation does not bypass that approval or the required app checks. If the installation suppresses those PR events entirely, close and reopen the PR as a maintainer to trigger the normal checks.
